# Database Views

[← Back to Database Overview](index.md)

The **Database Views** page lists the views that physically exist in the database.

It shows every view, whether or not the Framework has a definition for it, and provides actions to inspect a view, create a definition for it, or drop it.

## Overview

Use the Database Views page to:

- see which views exist in the database
- see which of them are linked to a relational object definition
- inspect a view's columns, its scripted SQL definition, and its data
- create a Direct SQL definition for a view that has none
- drop a view that is no longer needed

## Database View Record Fields

The following fields are shown for each database view.

| Field | Data Type| Purpose | Notes |
|---|---|---|---|
| Schema | int | The database schema the view belongs to. |
| View Name | nvarchar | The name of the view in the database. |
| Relational Object | int | The relational object definition linked to this view. | Blank where the view has no Framework definition.
| Relational Object Display Name | nvarchar | Display name of the linked relational object. |
| Relational Object Category Name | nvarchar | Category of the linked relational object. |
| Is Table | bit | Indicates the object is a table. |
| Is View | bit | Indicates the object is a view. |
| Is Stored Procedure | bit | Indicates the object is a stored procedure. |
| Is Custom | bit | Indicates the object is custom rather than part of the core product. |
| View Id | int | Identifier for the object record. |

## Actions

| Action | What it does | Notes |
|---|---|---|
| **Inspect View** | Inspect columns, the scripted SQL definition, and data. | Read-only. This is the quickest way to see the SQL a view was created with.
| **Add Definition** | Add a Direct SQL relational view definition. | Creates a Framework definition for a view that already exists in the database.
| **Drop View** | Drop the view from the database. | Removes the view. See the note below.

!!!Warning Drop View
    Dropping a view removes it from the database. Anything that reads through that view — models, views, or reports — will fail until it is recreated.

## Typical Use Cases

- Reviewing the SQL behind a view while troubleshooting
- Adopting a view created directly in SQL so the Framework can build on it
- Confirming a generated view was created as expected after a sync
- Removing a view left behind by earlier work

## Inspect a view

1. Go to **Admin | Relational | Database**
2. Open the **Views** page
3. Select the view
4. Click **Inspect View**

The inspection shows the view's columns, the SQL it was scripted from, and its data.

## Add a definition for an existing view

1. Go to **Admin | Relational | Database**
2. Open the **Views** page
3. Select a view that has no Relational Object shown
4. Click **Add Definition**
5. Review the created definition under [Relational Views](../relationalViews/index.md)

!!!Note Important Notes
    See [General Actions](../../../../concepts/metadataDrivenUI/actions.md#general-actions) for more information about working with records

## Notes

- Views generated by the Framework from a relational view definition also appear here — this page shows the database, not just externally created objects.
- Inspecting the scripted SQL is useful for checking how a generated view resolved its joins and expressions.
- A definition added here is a Direct SQL definition: the Framework references the view but does not manage its SQL.
